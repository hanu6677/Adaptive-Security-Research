# AI-Driven Adaptive Evasion Research Framework

A defensive cybersecurity research framework for studying how controlled, benign software variations affect **Windows security telemetry, behavioral visibility, event correlation, and detection coverage**.

The framework generates harmless program variants, executes them in a controlled Windows environment, collects available telemetry from Windows Event Logs and Sysmon, correlates the resulting events, measures behavioral visibility, and produces reports and dashboards for analysis.

> **Research Focus:** Defensive telemetry visibility and security monitoring research.

---

## Overview

Modern endpoint security systems rely heavily on behavioral telemetry such as:

* Process creation and termination
* File activity
* Network connections
* DNS queries
* Registry activity
* Windows system events
* Parent-child process relationships
* Event timestamps and execution timelines

This project provides a controlled environment for researching how these telemetry sources represent different **benign software variations**.

Instead of modifying malicious payloads or attempting to bypass security controls, the framework uses harmless Python samples and controlled source-code changes.

The objective is to answer questions such as:

> **How consistently can expected software behavior be observed through available Windows telemetry when the same benign workload is represented in different ways?**

## Key Features

### 1. Benign Sample Generation

Creates controlled Python research samples that perform harmless operations such as:

* Creating a temporary test file
* Reading test data
* Removing the test file
* Producing process and file activity

Each generated sample receives a unique research identifier.

---

### 2. Controlled Mutation Engine

The mutation engine creates safe source-code variations without introducing malicious functionality.

Supported research strategies include:

* `BASELINE_REPETITION`
* `CONTROLLED_SOURCE_VARIATION`
* `FILE_STRUCTURE_VARIATION`
* `PROCESS_STRUCTURE_VARIATION`

These variations allow researchers to compare telemetry generated by different representations of the same benign workload.

---

### 3. Windows Telemetry Collection

The framework can collect Windows Event Log information associated with controlled experiments.

Collected information may include:

* Event ID
* Timestamp
* Computer name
* Event source
* Record number
* Event category

---

### 4. Sysmon Telemetry

When Sysmon is available, the framework analyzes relevant Sysmon events.

Supported event categories include:

| Sysmon Event | Category               |
| -----------: | ---------------------- |
|            1 | Process Creation       |
|            2 | File Time Change       |
|            3 | Network Connection     |
|            5 | Process Termination    |
|            7 | Image Load             |
|           10 | Process Access         |
|           11 | File Creation          |
|           12 | Registry Create/Delete |
|           13 | Registry Value Set     |
|           14 | Registry Rename        |
|           15 | File Stream Created    |
|           22 | DNS Query              |
|           23 | File Delete            |
|           25 | Process Tampering      |

The framework normalizes these events into a common telemetry structure for further analysis.

---

### 5. Telemetry Correlation

The correlation engine combines telemetry from multiple sources and associates events with individual experiments.

It provides:

* Total event counts
* Internal telemetry
* Windows telemetry
* Sysmon telemetry
* Process events
* File events
* Network events
* Registry events
* DNS events
* Experiment timelines

---

### 6. Behavior Profile Analysis

The Behavior Profile Engine compares the behavior expected from a benign sample against the behavior actually observed in telemetry.

For the current sample, expected behavior includes:

```text
PROCESS → Expected
FILE    → Expected
NETWORK → Not expected
DNS     → Not expected
REGISTRY → Not expected
```

The engine calculates **expected behavior visibility** rather than claiming that an experiment successfully bypassed a security product.

---

### 7. Telemetry Visibility Metrics

The framework measures which telemetry categories were observed during each experiment.

Current categories:

* Process
* File
* Network
* DNS
* Registry

This provides a quantitative view of telemetry coverage across controlled experiments.

---

### 8. Adaptive Experiment Selection

The Adaptive Experiment Selector analyzes previous experiment results and chooses the next safe research strategy.

Example workflow:

```text
Previous Experiment
        ↓
Behavior Analysis
        ↓
Missing Expected Telemetry
        ↓
Adaptive Strategy Selection
        ↓
New Benign Experiment
```

The adaptive component is designed to improve research coverage rather than bypass endpoint security controls.

---

### 9. Timeline Analysis

The Timeline Analyzer organizes telemetry events according to their timestamps.

This allows researchers to examine the sequence of:

```text
Process Start
      ↓
File Activity
      ↓
Additional Telemetry
      ↓
Process End
```

The timeline can be used to investigate how different telemetry sources represent the same experiment.

---

### 10. Research Dashboard

The project includes an HTML-based dashboard for presenting experiment results.

The dashboard is designed to display:

* Experiment summaries
* Behavior visibility
* Telemetry coverage
* Process events
* File events
* Network events
* DNS events
* Registry events
* Timeline information
* Missing expected telemetry
* Experiment-level comparisons

## Sysmon Setup

Sysmon is optional for basic framework functionality but recommended for detailed Windows telemetry research.

After installing/configuring Sysmon, verify the service:

```powershell
Get-Service Sysmon*
```

Then verify the Sysmon event log:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 10 |
Select-Object TimeCreated, Id, ProviderName
```

The PowerShell terminal may need to be opened with **Administrator privileges** when accessing protected Windows event logs.

## Research Metrics

The framework currently focuses on two main metrics.

### Expected Behavior Visibility

Measures how much of the behavior expected from a controlled experiment was represented in the collected telemetry.

For example:

```text
Expected:
PROCESS
FILE

Observed:
PROCESS
FILE

Visibility:
100%
```

Another example:

```text
Expected:
PROCESS
FILE

Observed:
PROCESS

Visibility:
50%
```

This metric represents **telemetry visibility**, not malware detection or security-product bypass.

---

### Telemetry Category Coverage

Measures which telemetry categories were observed during an experiment.

```text
PROCESS
FILE
NETWORK
DNS
REGISTRY
```

For example:

```text
Observed:
PROCESS
FILE

Coverage:
2 / 5 categories
```

## Research Methodology

The project follows a controlled experimental methodology.

### Step 1 — Establish Baseline

Execute the original benign sample and record its expected behavior.

### Step 2 — Generate Controlled Variant

Create a harmless source-code variation.

### Step 3 — Execute in Controlled Environment

Run the sample locally in the research environment.

### Step 4 — Collect Telemetry

Collect available Windows and Sysmon telemetry.

### Step 5 — Correlate Events

Associate telemetry events with the corresponding experiment.

### Step 6 — Compare Behavior

Compare expected behavior against observed telemetry.

### Step 7 — Measure Visibility

Calculate behavior visibility and telemetry category coverage.

### Step 8 — Select Next Experiment

Use the previous result to select another safe research variation.

## Security and Ethical Considerations

This project is intended for **defensive cybersecurity research and education**.

The framework deliberately avoids functionality designed to:

* Create malware
* Generate ransomware
* Generate reverse shells
* Steal credentials
* Establish persistence
* Evade or disable security products
* Modify malware to defeat antivirus detection
* Bypass EDR protections
* Perform unauthorized access
* Conduct attacks against third-party systems

All experiments should be performed on systems that the researcher owns or is explicitly authorized to test.

The term **"adaptive evasion research"** in this project refers to studying how controlled benign software variations affect telemetry visibility. It does not imply operational malware evasion.

---

## Limitations

The quality of telemetry analysis depends on the Windows configuration and available monitoring sources.

In particular:

* Windows System Event Logs do not provide complete process/file telemetry.
* Sysmon provides significantly richer endpoint telemetry when correctly configured.
* Some Windows logs require elevated privileges.
* Telemetry availability depends on installed and enabled monitoring components.
* Event timestamps may originate from different sources and require normalization.
* Absence of an event does not necessarily mean that an activity did not occur.
* The framework measures telemetry visibility rather than commercial EDR detection effectiveness.

## Research Objective

The primary objective of this project is to build a controlled platform for understanding the relationship between **software behavior and endpoint telemetry**.

By combining controlled experiments, Windows telemetry, Sysmon, event correlation, behavioral analysis, adaptive experiment selection, and visualization, the framework can help researchers identify where expected activity is visible, where telemetry is incomplete, and how monitoring configurations influence security research results.
